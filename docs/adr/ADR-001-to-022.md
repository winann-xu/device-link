> 格式：问题 → 根因 → 决策 → 理由
> 共 22 条，按发现时间排列。

## ADR-001: add_device 默认值空字符串（Bug A）

- **问题**: 添加设备时未传可选字段 → 存成空字符串（`is_enabled=''`, `port=''`）→ 后续类型错误
- **根因**: `device_dict.get(f, '')` 用空串兜底，int/bool 字段预期数字
- **决策**: 用 DEFAULTS 字典为每个字段提供合理默认值（port=0, is_enabled=1, timeout_ms=3000 等）
- **理由**: 数据库 schema 有 DEFAULT 值，Python 侧应与之一致；空串是 SQLite 的默认行为但不能依赖

---

## ADR-002: SQLite 跨线程 check_same_thread=False（Bug B）

- **问题**: 多线程访问同一 SQLite 连接抛 `sqlite3.ProgrammingError`
- **根因**: Python sqlite3 默认禁止跨线程使用同一 Connection 对象
- **决策**: 初始设为 `check_same_thread=False`（后续 ADR-020 证明不够，改为连接池化）
- **理由**: 调度器线程池需要从 worker 线程读写数据库

---

## ADR-003: DigestEngine 容量上限未实现（Bug C）

- **问题**: `flush()` 返回全部缓冲事件，不按 `max_events_per_digest` 截断
- **根因**: 规则 3（容量上限）写了注释但未实现截断逻辑
- **决策**: `flush()` 内截断，超出部分留在缓冲区进入下一窗口，分配新 digest_id
- **理由**: 告警风暴时单封摘要邮件包含几百条事件不可读；截断保证每封邮件上限可控

## ADR-004: UNKNOWN 状态漏报（Bug D，严重）

- **问题**: 从未上线过的设备连续失败永不触发告警（`failure_count` 恒为 1）
- **根因**: UNKNOWN 分支失败时计数器未累计；每次 `transition()` 重新赋值为 1
- **决策**: UNKNOWN 分支累计 `failure_count += 1`，达到阈值 → OFFLINE + `device_offline` 事件
- **理由**: 启动时已离线的设备必须能被检测到；漏报率为零是底线要求

---

## ADR-005: UI 四页面加载失败（Bug E）

- **问题**: 主窗口启动但仪表盘/设备管理/告警配置/历史统计全部加载失败
- **根因**: 两处：(1) `main_window.py` 用 `addWidget(page)` 但 page 类不是 QWidget 子类 (2) `history_panel.py` 类型注解 `QFrame` 未导入 → NameError
- **决策**: 改为 `addWidget(page._widget)` + QFrame 提到模块顶部导入
- **理由**: 组合模式优于继承时统一用 `._widget` 暴露内部控件

## ADR-006: PyInstaller frozen 模式路径错误（Bug F）

- **问题**: 打包后 exe 把 config/data/logs 写进 `%TEMP%\_MEI*`（退出消失），不满足便携版要求
- **根因**: `Path(__file__).parent.parent` 在 frozen 模式指向临时解压目录而非 exe 所在目录
- **决策**: 用 `getattr(sys, 'frozen', False)` 检测；打包模式数据根 = `Path(sys.executable).parent`
- **理由**: 便携版硬性要求——所有运行时数据落 exe 旁目录，不依赖 AppData/TEMP

## ADR-007: shutdown() timeout 参数 TypeError（Bug G）

- **问题**: `MonitorScheduler.stop()` 调用 `self._executor.shutdown(wait=True, timeout=10)` 必抛 TypeError
- **根因**: `ThreadPoolExecutor.shutdown()` 无 `timeout` 参数（Python 3.9+ 仅有 `cancel_futures`）
- **决策**: 改为 `shutdown(wait=True, cancel_futures=True)`，探测本身有硬超时保护
- **理由**: 优雅关闭依赖 stop() 不抛异常；cancel_futures 取消排队任务，运行中任务自然完成

---

## ADR-008: 摘要泵重复刷新（Bug H）

- **问题**: DigestEngine 定时刷新逻辑存在竞态，产生空摘要或重复批次
- **根因**: 定时器与 `flush()` 调用之间缺同步，`should_flush()` 和 `flush()` 非原子
- **决策**: 在 `flush()` 和 `add_event()` 关键路径加锁；`should_flush()` 返回 False 时不重置定时器
- **理由**: 空摘要邮件会造成告警噪音；重复批次浪费通知配额

---

## ADR-009: 并发 execute 数据踩踏（Bug I）

- **问题**: 多线程并发 `execute()` 导致 `no more rows available` / `bad parameter`
- **根因**: ADR-002 的 `check_same_thread=False` 允许多线程用同一 Connection，但 C 层游标状态非线程安全
- **决策**: 加全局 `_DB_LOCK`（RLock）串行化所有仓储公共方法的数据库访问
- **理由**: 后续 ADR-020 证明 Python 锁不能彻底解决 C 层问题，此处只是过渡方案

---

## ADR-010: digest.enabled=False 不立即发送（Bug J）

- **问题**: 摘要关闭时离线告警仍丢进缓冲区等窗口，用户收不到即时通知
- **根因**: `alert_engine.on_monitor_event()` 未检查 `digest.enabled` 开关
- **决策**: 摘要关闭直接走 `_send_immediate()`；摘要开启走缓冲区合并
- **理由**: 摘要合并是可选项，关闭时应保留即时通知的基本功能

---

## ADR-011: notify_success 不落库（Bug K）

- **问题**: 通知发送结果从未写入 `alert_events` 表，无法追溯是否送达
- **根因**: `_send_immediate` 和 `_send_digest` 只计算 `notify_success` 值但未调仓储写入
- **决策**: 新增 `AlertRepository.update_notify_result()` 方法，发送后立即写入
- **理由**: 运维排查需要知道某条告警是否已通知成功；升级引擎也依赖此状态

---

## ADR-012: ping 异常分类被 AttributeError 顶掉（Bug L）

- **问题**: 任何探测异常的分类逻辑全部失效
- **根因**: `except ping_errors.PermissionError` —— `ping3.errors` 模块无 `PermissionError` 属性，访问时 `AttributeError` 覆盖原异常
- **决策**: 在通用 `except OSError` 内按 `isinstance(e, PermissionError)` 或字符串匹配分类
- **理由**: 跨平台 ping 库的异常类型不稳定，不应直接引用可能不存在的属性

## ADR-013: 看门狗 os.kill(pid,0) 在 Windows 杀死主进程（Bug M，严重）

- **问题**: 应用启动后 15-60 秒自动闪退，日志显示"父进程已退出"
- **根因**: `os.kill(pid, 0)` 在 Unix 是空操作（仅检查进程存活），在 Windows 调用 `TerminateProcess()` 实际杀死进程。看门狗每 15 秒调用 `os.kill(os.getpid(), 0)` → 自杀
- **决策**: 新增 `_is_process_alive()` 方法，Windows 用 `tasklist /FI "PID eq N"` 查询，Unix 保留原逻辑
- **理由**: Windows 没有 Unix 信号模型，`os.kill()` 行为完全不同。跨平台进程存活检查必须分平台实现

## ADR-014: sqlite3.dll ACCESS_VIOLATION 0xc0000005（严重）

- **问题**: `python.exe` 崩溃，事件日志显示 `sqlite3.dll` 访问违例
- **根因**: `main.py` 在主线程创建 1 个 Connection 传给所有 Repository，worker 线程共享同一 C 层句柄。`check_same_thread=False` 绕过 Python 保护但 C 层仍不安全
- **决策**: (1) 每线程通过 `threading.local()` 获取独立 Connection (2) Repository 改 `@property` 惰性获取 (3) 去掉 `check_same_thread=False`
- **理由**: SQLite WAL 模式天然支持多连接并发读；独立连接从根本上消除跨线程共享句柄的风险

## ADR-015: UI 状态列 GlobalColor 不接受字符串（Bug N）

- **问题**: 设备管理表格空白，添加设备弹"not a valid Qt.GlobalColor"
- **根因**: `Qt.GlobalColor(colors.get(status, 'grey'))` 不接受 hex 颜色字符串如 `#52C41A`
- **决策**: 改用 `QColor(colors.get(status, '#8C8C8C'))`，支持 hex 和颜色名
- **理由**: QColor 构造函数接受所有标准颜色格式，兼容性远好于 GlobalColor 枚举

## ADR-016: 历史统计在线率卡死代码（Bug O）

- **问题**: 今日/本周/本月在线率永远显示 "--"
- **根因**: `findChild(type(widget), "stat_")` 找错对象 + `pass` 空操作，计算结果从未 setText

- **理由**: 历史统计是用户核心关注指标，死数据严重损害信任

## ADR-017: 告警日志表永远空表（Bug P）

- **问题**: 历史页告警日志表无数据
- **根因**: `HistoryPanel` 从未接收 `alert_repo`，没有填充逻辑

## ADR-018: 切页不刷新数据（Bug Q）

- **问题**: 切到设备管理/历史统计页不加载数据，只有点按钮才刷新
- **根因**: `_on_nav_changed` 用 `_stack.widget(row)`（返回 QWidget）找 `refresh()`，但方法在面板类上 → `hasattr` 恒为 False
- **决策**: 维护 `self._pages` 面板列表，切页时调对应面板的 `refresh()`；异常升为 ERROR
- **理由**: QStackedWidget 的 widget 索引对应关系不可靠，显式面板列表更清晰

## ADR-019: combo 信号递归栈溢出（Bug R）

- **问题**: `DEVICE-LINK.exe` 崩溃 `0xc00000fd`（Qt6Gui.dll 栈溢出）
- **根因**: 设备下拉框 `currentIndexChanged` → `refresh()` → 重建 combo → 再次触发信号 → 无限递归
- **决策**: `combo.blockSignals(True)` 保护重建段 + `_refreshing` 重入标志防止并发刷新
- **理由**: Qt 信号在 UI 重建时极易形成循环；blockSignals + 重入标志是 Qt 编程的标准防护模式

## ADR-020: 卡片文字不显示（Bug S）

- **问题**: 仪表盘卡片框架正常但内部设备名/IP/状态文字完全不绘制
- **根因**: QFrame widget 级 QSS `padding: 12px` 在 PySide6 6.11.1 环境下导致子 QLabel 不渲染（几何正常、UIA 有文本、像素/OCR 均无字）
- **决策**: 删除卡片 QSS 的 padding（QVBoxLayout margins 已承担间距）
- **理由**: widget 级 QSS padding 副作用是 PySide6 版本特定 bug，用布局 margin 替代更稳健

## ADR-021: 时间按钮白字白底（Bug T）

- **问题**: 历史页"今天/7天/30天"三个按钮渲染为白底空框
- **根因**: 全局 QSS `QPushButton { color: white }` → 按钮 widget 级 QSS 只设 `background: white`，缺 `color` → 继承全局 white → 白字白底
- **决策**: 按钮 QSS 显式加 `color: #333`
- **理由**: QSS 继承规则——widget 级覆盖 background 时务必同时覆盖 color，防止被全局样式吞掉

## ADR-022: sync 脚本覆盖运行数据库

- **问题**: `sync_from_claude.py` 把 50.53 的 `device-link.db` 覆盖到 50.20 正在运行的进程打开的文件 → `integrity_check` 报 btree 损坏（几百页 error 11）
- **根因**: 同步脚本无白名单/黑名单，运行数据被当作源码同步；写入时未检查文件是否被占用
- **决策**: sync 加白名单（仅 src/config/assets/tests/docs/build），排除 data/logs/dist；写入前检查目标是否被进程占用
- **理由**: 运行数据与源码必须隔离；覆盖已打开的 SQLite 文件必然损坏 WAL/journal

## ADR-023: 历史数据自动清理（保留 30 天）

- **问题**: `data/device-link.db` 随探测持续膨胀（1143 台 120 秒间隔 ≈ 88 万行/天，
  30 天窗口近 2600 万行）；`storage.history_retention_days` 与
  `HistoryRepository.cleanup_expired()` 虽早已存在，但**没有任何调用方**，
  配置项形同虚设，实测生产库数据无上限增长（主库 2490.8MB + WAL 5711.7MB = 8.2GB）
- **决策**: 新增 `src/storage/maintenance.py` + 后台线程 `DataRetentionWorker`：
  默认保留 30 天、每 60 分钟一轮、每批删除 5000 行、批间 50ms 让出写锁、
  单轮上限 200 万行；清理后 checkpoint + 增量回收 + `PRAGMA optimize`；
  `journal_size_limit=64MB`；新增 `--vacuum-now` 离线维护命令整库 VACUUM
- **理由**: 一次性 `DELETE` 千万行会长时间独占写锁（探测落库全部报 database is
  locked，生产日志里已有 124 次这类报错）—— 分批 + 让锁 + 单轮上限让清理与监控共存；
  旧配置默认 90 天按新策略 30 天执行并写 WARNING，显式写 `cleanup.retention_days`
  则完全尊重用户设置

## ADR-024: 历史统计改为日汇总表 + 索引补齐

- **问题**: 历史页「全部设备」在线率按 `checked_at` 范围统计，而唯一相关索引是
  `idx_sh_device_time(device_id, checked_at)`，前导列不匹配 → 全表扫描；
  1728 万行基准库实测一次历史页刷新 97.2s（全部设备）/40.7s（单台）
- **决策**: 分两层解决
  1. 索引层：新增 `idx_sh_checked_status(checked_at, status)`（保留期清理 +
     在线率回退统计）与 `idx_sh_offline(device_id, checked_at) WHERE status='offline'`
     （部分索引，只含离线行）；启动时 `ensure_indexes()` 幂等补建并记录耗时。
     实测只加索引：离线排行榜 38.7s → 0.02s，全局在线率 38.9s → 1.7s，
     但"全部设备"刷新仍 2.2s（30 天窗口要数 2600 万行），规模更大时不可接受
  2. 汇总层：新增 `status_daily`（设备×日期计数，WITHOUT ROWID），每次探测在
     同一事务内累加；历史页统计改读该表（1143 台 × 30 天 ≈ 3.4 万行）→ 实测 4.5ms。
     老库首次升级自动回填（一次扫描，幂等覆盖），之后每轮只重算最近 2 天；
     日汇总缺失时回退扫描明细，口径不变
- **理由**: 明细表是"每次探测一行"的写密集结构，用索引优化只能把常数因子降下来；
  统计类查询本质是聚合，预聚合才是数量级的解法。写侧代价实测 +0.73ms/次探测（可忽略）。
  未保留三列覆盖索引 `(device_id, checked_at, status)`：它要多占约 1/3 索引空间，
  而统计已改读日汇总表，不值得为罕见回退路径长期付出体积代价；
  离线排行榜回退查询同时改为"离线行聚合派生表"写法（旧 LEFT JOIN 在缺宽索引时
  优化器会退化成按设备扫全部行，实测 49.8s → 0.015s），回退统计用两次 `COUNT(*)`
  而非 `SUM(CASE)`（覆盖索引下 COUNT 是纯索引区间计数，实测快约 1 倍）
